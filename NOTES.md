# NOTES — выводы из документации и расхождения с промптом

Дата: 2026-10-28. Проверено по документации, не по промпту.

## Telegram Bot API

1. **`sendMessageDraft` существует** и документирован:
   `https://core.telegram.org/bots/api/methods/sendmessagedraft`.
   Параметры: `chat_id`, `draft_id` (не `random_id`, как в MTProto-API; **должен быть не нулём**;
   одинаковый `draft_id` → анимированное обновление), `message_thread_id`, `text` (0–4096 после
   entities-parsing; **пустая строка = плейсхолдер «Thinking…»**), `parse_mode`/`entities`,
   `can_stop` (кнопка «остановить генерацию», приходит update `stopped_message_generation`),
   `keep_on_stop`.
2. Драфт **эфемерный (~30 с)**: для финала обязателен обычный `sendMessage` — это совпадает с промптом.
   Драфт исчезает при обычном сообщении в чате.
3. Live-драфты работают только в личных чатах с пользователями.
4. Рейтлимиты на чат (общие для `sendMessageDraft`/`sendChatAction`): **20 вызовов / 5 с** и
   **40 вызовов / 30 с**; при превышении `FLOOD_WAIT_%d` (короткие кулдауны ≤ 3 с возможны даже
   при аккуратном троттлинге). Стратегия: ≤ 1 кадра в ~0.9 с + ≥ N новых символов; при
   `TelegramRetryAfter` спать указанное время, пропускать промежуточные кадры, финальный кадр — обязательно.
5. Update `stopped_message_generation` при нажатии кнопки остановки (`can_stop=True`).

## aiogram

- Установлена **aiogram 3.31.0** (актуальная на момент работы). В ней **УЖЕ ЕСТЬ** `SendMessageDraft`
  (`aiogram.methods.SendMessageDraft`, метод `__api_method__ = "sendMessageDraft"`) и хелпер
  `bot.send_message_draft(...)`, а также `SendRichMessageDraft`. Кастомный `TelegramMethod`
  поверх `bot.session` **не потребовался** — промпт предполагал, что его придётся писать.
- При ошибке `send_message_draft` (метод недоступен у апстрима/старый Bot API) `DraftStreamer`
  автоматически откатывается на `send_message` + `edit_message_text` — фолбэк оставлен.

## OpenRouter

1. **`anthropic/claude-haiku-5.5`** — Chat Completions (`POST /api/v1/chat/completions`).
   Поддерживает: `tools`, `tool_choice`, `response_format` (json_schema), `reasoning`,
   `max_tokens`/`max_completion_tokens`. Аудио **не принимает** — только текст и изображения.
2. **Reasoning**: единый параметр `reasoning: {"effort": "low"|"medium"|..., "exclude": true}`.
   `exclude: true` прячет reasoning из ответа (токены всё равно биллятся и едят `max_tokens`,
   поэтому `max_tokens` ставим с запасом). Для оркестратора/судьи используем `effort: "low"` +
   `exclude: true` — не полагаемся на добровольное молчание модели.
3. **Tool calling** — стандартный OpenAI-совместимый формат: `tools: [{type:"function", function:{name, description, parameters}}]`,
   ответ приходит в `choices[0].message.tool_calls[].function.arguments` (строка JSON);
   `tools` нужно передавать в каждом запросе. Используем «принудительный» tool
   (`tool_choice: {type:"function", function:{name:...}}`) для строгого JSON-плана и судьи,
   поверх Pydantic-валидация и один repair-retry.
4. **`krea/k3-edit` — не через Chat Completions и не через `modalities`**, как было в промпте.
   Это dedicated **Image API**: `POST https://openrouter.ai/api/v1/images`:
   - `model: "krea/k3-edit"`, `prompt`, `n` (у этого провайдера фактически 1),
   - `input_references`: до **8** картинок, элементы `{type:"image_url", image_url:{url}}`
     (https-URL или **base64 data-URL**);
   - `aspect_ratio`: `"1:1"|"4:3"|"3:2"|"16:9"|"4:5"|"2:3"|"9:16"` (этот набор — для k3-edit;
     другие модели принимают шире), `resolution: "1K"|"2K"`;
   - **`seed` поддерживается** (integer, опционально), но детерминизм не гарантирован —
     в описании результата не обещаем воспроизводимость;
   - ответ: `{"data":[{"b64_json": "...", "media_type":"image/png"}], "usage": {...cost...}}` —
     картинка приходит в `data[0].b64_json` (base64), НЕ в chat-сообщении;
   - ошибки: 413 — тело слишком большое (важно: картинки-референсы заранее сжимаем/ресайзим);
     429/502 — ретраи; биллинг all-or-nothing (упавшая генерация не билится).
5. **Vision (вход картинок)**: Chat Completions, `content` — массив, текст **первым** элементом,
   затем `{type:"image_url", image_url:{url:"data:image/jpeg;base64,..."}}`.
6. **STT есть**: `POST /api/v1/audio/transcriptions` — JSON с base64 `input_audio:{data, format}`
   (`ogg` поддерживается) или OpenAI-совместимый multipart; ответ `{text, usage{...cost}}`.
   Модель, например, `openai/whisper-1`. Поэтому облачный `Transcriber` реализуем через этот
   эндпоинт (переменная `STT_MODEL`), по умолчанию — `cloud` (OpenRouter).
7. Ретраи: 429/5xx с экспоненциальной паузой; 502 — «failed upstream, not billed».
8. **Облачная STT-модель по умолчанию: `mistralai/voxtral-small-transcribe-3-0`**
   (эндпоинт тот же — `POST /api/v1/audio/transcriptions`, `input_audio:{data, format}`,
   тарификация ~$0.000073/сек аудио). Пример в карточке модели показывает `"format": "wav"`,
   но таблица поддерживаемых форматов STT API включает `ogg`; для голосовых Telegram
   шлём `format: "ogg"`, при отказе провайдера — конвертация в wav через ffmpeg (fallback
   в `CloudTranscriber`).

## Окружение / прочее

- В dev-окружении установлен **Python 3.14** (промпт просил 3.12) — код совместим с 3.12+;
  в Dockerfile пин `python:3.12-slim`. Всё, что используется, доступно и в 3.12.
- aiogram 3.31.0 требует Python ≥ 3.9, ок.
- `faster-whisper` тяжёлый: делаем **ленивый импорт** и ленивую загрузку модели `small` (int8, CPU),
  чтобы бот стартовал без него, если STT не нужен. `STT_PROVIDER=local|cloud` (по умолчанию local).
- `sendMessageDraft` — новый метод: на старых Bot API вернётся 404/BadRequest → фолбэк на
  send/edit реализован и покрывается `/selfcheck`.
- У OpenRouter для картинок-референсов лимит 8: молд всегда №1 + до 7 текстур/референсов;
  больше 7 текстур → несколько последовательных проходов по группам поверхностей.

## Реализация: решения по ходу работы

- **aiogram 3.31.0 уже содержит `SendMessageDraft`** (`aiogram.methods.SendMessageDraft`,
  хелпер `bot.send_message_draft(...)`) — кастомный `TelegramMethod` поверх `bot.session`
  **не понадобился**. Фолбэк на `send_message` + `edit_message_text` (если метод недоступен
  у Bot API) реализован в `DraftStreamer`, проверяется при старте и в `/selfcheck`.
- `DraftStreamer._last_send: float | None = None` («ещё ни одного кадра»): первый кадр всегда
  уходит в драфт, дальше — двухуровневый токен-бакет (интервал ~0.9 с И минимум N новых
  символов). При `TelegramRetryAfter` спим указанное время, пропуская промежуточные кадры, и
  обязательно доставляем последний; финал — обычный `send_message` (драфты эфемерны, ~30 с).
- **K3 Edit через Image API `/api/v1/images`** (не через chat-композиции, как предполагал промпт):
  молд — референс №1, затем текстуры; ответ — `data[0].b64_json`; `seed` передаётся, но
  детерминизм не обещаем; варианты параллельно (`Semaphore(4)`) с ретраями 429/5xx и таймаутами.
- **Качество изображений** (правка после жалобы на агрессивное сжатие):
  генерация идёт в `IMAGE_RESOLUTION=2K` (enum K3 Edit: 1K/2K, при отказе модели — автофолбэк
  на 1K), входы генерации (молд/текстуры) ресемплятся в `GEN_MAX_SIDE=2048`, внутренние входы
  судьи и SSIM — `SCORE_MAX_SIDE=1024` (не видны пользователю); повторные кодеки — JPEG
  `JPEG_QUALITY=95`; загруженные пользователем файлы хранятся **как есть** (без пережима,
  пережим только при отправке модели); результат в чате — фото (Telegram пережимает превью),
  полная версия — теперь и есть основная отправка (всё документами, см. ниже).
  Миниатюры `/history` — 128px q70.
- **Подача и выдача (правка «все фотки документами + один этап»)**:
  все картинки уходят `send_document` (победитель, варианты, `/history`, `/files`, галерея) —
  кнопки «Показать все» и «Оригинал» удалены как излишние; варианты шага отправляются
  автоматически сразу после победителя, нумерация по скору (№1 = победитель), остальные —
  `Вариант №N`. Подпись на фото/альбоме = бриф → мгновенный запуск (`_brief_from_caption`,
  префикс роли отрезается); одиночная прикреплённая картинка передаётся оркестратору как
  `attached` — при правке он предпочитает её как базу. Текстовый бриф без картинки → галерея:
  `_base_gallery` = **варианты активного шага** (is_winner первым, затем по `score_json.total`,
  до 9, только существующие файлы; fallback на загрузки только до первой генерации, где
  texture/reference называет модель по `files.analysis`, не caption) → документы
  «№N — …» + кнопки «Править №N» (`editbase:<token>:<n>`, хранилище `_PENDING_BASE_CHOICES`,
  TTL 10 мин, peek/pop — неверный тап не теряет бриф) → `base_override` жёстко ставит базу.
  `chat`/`ask_clarification` галерею не показывают. Фидбэк при загрузке — нумерованные
  «инструментальные» блоки viewer-фазы (`🔧 Шаг #N · смотрю изображение` + стриминг, затем
  `🔧 Шаг #N · анализ`), ✅-строки с caption удалены; `_clean_caption` не даёт промпту
  стать названием файла (роль или ≤40 символов).
- **Оркестратор и судья**: tool use с `tool_choice={"type":"function"}` + Pydantic-валидация,
  **один repair-retry** с текстом ошибки, затем понятное сообщение пользователю;
  `reasoning: {"effort":"low","exclude": true}` — reasoning не попадает в чат.
- **Фаза просмотра (viewer)**: перед планированием бот «смотрит» новые изображения —
  по одному vision-вызову на файл (`chat_stream` → текст пишется в блок-цитату через
  `QuoteStreamer`, редактируется на месте с троттлингом 1.2 с), описание кэшируется в
  `files.analysis` (миграция v2), затем идёт блок «🧭 Как применю материалы»
  (синтез со стримингом). Лимит — `MAX_VIEW_FILES=6` на бриф; просмотренные файлы
  повторно не смотрятся (только кэш подмешивается в контекст). Оркестратор получает
  `sees:` в строках файлов + `Viewer's synthesis` — теперь он реально «видит» картинки.
- **Судья смотрит на картинки сам** (инвариант, закреплён тестом `test_judge_vision.py`):
  `Judge.score` кладёт в vision-запрос base64 молда, каждой текстуры и самого кандидата;
  описания зрителя (`viewer_notes`) ему НЕ передаются — они только для планирования.
- **Голос**: STT через `Transcriber` — по умолчанию облачный OpenRouter
  `mistralai/voxtral-small-transcribe-3-0` (не требует ffmpeg), опция `STT_PROVIDER=local` —
  faster-whisper small/int8; расшифровка показывается строкой «🎙 …».
- **Лимиты**: `n_variants ≤ MAX_VARIANTS` (клампится), референсы ≤ 8 (молд + 7), больше 7
  текстур → несколько проходов по группам поверхностей, `DAILY_IMAGE_LIMIT` считается по
  таблице `usage`.
- **Очередь**: один активный запрос на чат (по chat_id), повторный запрос ставится в очередь с
  уведомлением; `/cancel` отменяет активную задачу.
- **Тесты**: `pytest` (51 тест) и `ruff check` зелёные. Покрыты: `clean_output`, конвертер
  Markdown→HTML (включая закрытие незавершённой разметки при стриминге), `DraftStreamer`
  (троттлинг, FLOOD_WAIT, фолбэк send/edit), CRUD инструкций, валидация и repair JSON
  оркестратора, логика отката, подсчёт лимитов, SSIM-метрика.
